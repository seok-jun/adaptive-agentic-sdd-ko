# 개념

## 실행 명세로서의 작업 항목

현재 작업 항목(GitHub Issue, Jira 티켓, Linear issue 또는 동등한 시스템)은 요청된 **TO-BE**를 소유합니다.

- 사용자·비즈니스 영향,
- 목표,
- 범위,
- 수정 허용·금지 경계,
- 인수 조건,
- 의존성과 blocker,
- 권위 있는 참조에서 이미 확정된 결정.

작업 항목에 현재 구현 전체를 담으려 하지 않습니다. 현재 구현은 AS-IS 분석의 책임입니다.

## AS-IS와 TO-BE

다음과 같이 분리하면 유용합니다.

```text
현재 메인라인 코드 = 관찰된 AS-IS
현재 작업 항목      = 요청된 TO-BE
```

기능 개발 중 두 상태가 다른 것은 정상입니다.

오래된 문서가 현재 구현과 다르다는 이유만으로 코드를 “수정”하지 않습니다.

## 점진적 공개(Progressive Disclosure)

에이전트는 작고 안정적인 저장소 진입 계약에서 시작하고 현재 작업이 요구할 때만 더 깊은 규칙을 읽어야 합니다.

```text
AGENTS.md -> 작업 Skill -> 조건부 process/domain docs
```

이 구조는 토큰 최적화일 뿐 아니라 정확성 메커니즘이기도 합니다. 진입 경로는 안정적으로 유지하면서 상세 정책은 가장 좁고 관련성 높은 문서가 소유합니다.

## 제한된 추론(Bounded Reasoning)

구체적인 의존성, 컴파일 실패, 인수 조건, 계약, 충돌이 요구할 때만 컨텍스트를 확장합니다.

목적은 어떤 경우에도 생각을 최소화하는 것이 아닙니다. 일상 작업에서 경계 없는 재탐색을 피하는 것입니다.

## 검토 증거와 Human 승인

독립 검토는 제안이나 구현에 대한 증거를 만듭니다. 그것만으로 Human 승인이 생기지는 않습니다.

Human 승인이 필요하면 실제 Human에게 제시한 phase, artifact revision, decision scope에 승인을 귀속합니다. 의미가 바뀌는 revision 변경에는 변경된 의미에 대한 새 승인이 필요합니다.

## 증거

완료는 변경에 맞는 증거로 뒷받침되어야 합니다.

- unit test,
- integration test,
- lint·static analysis,
- build·package 검증,
- CI,
- 독립 검토,
- 필요한 경우 Human 승인,
- 실기기·런타임 QA.

“실행하지 않음”은 “통과”와 같지 않습니다.
