# 워크플로

이 문서는 작업 생명주기의 기준 문서입니다. [위험 등급](risk-grades.md), [검토 게이트](review-gates.md), [검증](verification.md)은 각각의 계약을 정의합니다. 도식·예시·개발자 가이드는 이를 설명하며 기준 문서를 덮어쓰지 않습니다.

## 0. 도입

작은 루트 지침과 작업 Skill을 도입하기 전에 실제 모듈 경계, 작업 관리 시스템, 빌드·테스트 경로, 기존 규칙을 확인합니다. 환경별 보호 규칙은 프로젝트 로컬에 둡니다. [도입 가이드](bootstrap.md)를 참고하세요.

## 1. 작업 항목과 사전 점검

수정 전에 다음을 확정합니다.

- 현재 작업 항목의 식별자·리비전 또는 신뢰할 수 있는 스냅샷
- 목표, 사용자·업무 영향, 우선순위, 등급, 이미 확정된 결정
- 작업 범위·제외 범위, 수정 허용·금지 경계
- 인수 조건(AC), 입증 방법, 의존성·차단 요인, 기준 출처
- 요청받은 행위와 사용 가능한 기능: 계획, 구현, 검증, 검토, 커밋, 통합

필수 경계 누락, 기준 요구사항 충돌, 해결되지 않은 의존성, 해당 단계의 권한 누락은 수정을 차단합니다. 등급은 파일 종류나 구현 시간이 아니라 위험에 따라 결정합니다.

읽기 범위와 수정 범위는 다릅니다. 변경을 이해하는 데 필요한 직접 의존 관계는 확인하되, 승인된 경계 밖은 수정하지 않습니다. 범위 밖 수정이 필요하면 멈추고 범위를 갱신받습니다.

## 2. 필요한 경우 작업 소유권과 격리

병렬 작업에는 작업 레인 소유권, 중복 작업 확인, 독립 브랜치·worktree·sandbox가 필요할 수 있습니다. 이는 로컬 운영 확장이며 모든 저장소에 강제하는 절차가 아닙니다. 관련 없는 사용자·팀 변경을 보존합니다.

## 3. 제한된 AS-IS 분석

현재 메인라인 코드와 직접 런타임 증거에서 시작합니다. 직접 대상 경로, 심볼, 공개 계약, 호출자·피호출자, 관련 지속 문서 순으로 확인합니다. 구체적인 불확실성이 있을 때만 탐색을 넓힙니다.

관찰된 동작, 증거, 미확인 사항, 경계, 의미 있는 문서 불일치를 기록합니다. Trivial은 별도 산출물을 생략하고, Small은 작업 항목이나 메모를 사용할 수 있습니다.

**Large 게이트:** AS-IS 결론을 확정된 PLAN 기준으로 사용하기 전에 독립 AS-IS 검토로 관찰·계약의 차단 결함을 해결해야 합니다. AS-IS 대상 리비전과 판정을 기록합니다.

## 4. TO-BE·변경 계획·검증 전략

원하는 동작과 보존할 동작, 실패 동작, 필요한 상태 전이, 변경 순서, AC와 증거의 대응, 롤백 점검 대상을 정의합니다. 실제로 경쟁하는 선택지가 있을 때만 트레이드오프를 기록합니다.

Medium 이상은 명시적인 섹션을 사용하되 별도 파일은 선택 사항입니다. Epic은 먼저 독립적으로 검증 가능한 하위 작업으로 나누고 통합 책임을 지정합니다.

**Large 게이트:** PLAN(TO-BE와 변경 계획)을 고유 대상 리비전으로 독립 검토합니다. 차단 사항을 해결하고 사람이 결정권을 가진 설계는 승인을 받습니다. AS-IS PASS는 PLAN PASS나 구현 허가가 아닙니다.

## 5. 구현

허가된 작업만 구현합니다. 승인된 결정·계약을 보존하고 관련 없는 리팩터링, 기능 추가, 이름 변경, 의존성 변경을 섞지 않습니다. 필요한 직접 회귀 검증을 추가합니다. 새로운 위험이나 범위 변경이 드러나면 등급을 올리거나 승인을 위해 멈춥니다.

## 6. 검증과 자체 검토

대상 중심 검사를 먼저 실행하고 변경 영향에 따라 더 넓은 검사를 수행합니다. 중요한 AC마다 기대 동작, 실제 관찰, 대상 리비전·환경, 상태, 증거를 연결합니다.

diff를 AC, 범위, 수정 허용·금지 경계, 확정된 결정, 의도하지 않은 변경과 비교합니다. 자체 검토는 독립 검토가 아닙니다. 실행하지 않은 검사는 절대 PASS가 아닙니다.

## 7. 지속 문서와 최종 후보

제품·런타임 동작이 변경되면 계획 문구를 복사하지 않고 최종 관찰된 코드 동작에 맞춰 지속 문서를 동기화합니다. 후보에 대해 최종 필수 검사를 실행합니다. 문서 변경이 실행·계약 의미를 바꾸면 해당 변경도 검증·검토 범위에 포함합니다.

## 8. 필요한 독립 CODE 검토

Large와 Large 수준의 Epic 작업 레인은 독립 코드 검토가 필요합니다. Medium은 계약·통합 위험이 정당화할 때 범위를 제한한 독립 검토를 사용합니다. [검토 게이트](review-gates.md)를 적용하며 작성자에게 독립성을 스스로 인증하게 하지 않습니다.

검토 후 의미 있는 변경이 생기면 영향받는 검사·검토를 다시 수행합니다. 선택적 Blind Audit은 지적사항을 대조하기 전에 별도의 최초 판정을 남깁니다.

## 9. 필수 런타임 증거와 준비 상태

AC가 요구하면 실기기·브라우저·통합 환경·런타임 관찰을 수집합니다. 검증 중 수행해도 되지만 최종 허가 전에는 완료해야 합니다. [실기기 QA](device-qa.md)를 참고하세요.

범위, AC 결과, 검토 증거, 의미 있는 결정, 문서 동기화, 제한 사항을 PR 또는 동등한 후보 보고서에 정리합니다. 필수 FAIL·BLOCKED·UNVERIFIED, 필요한 검토 누락, 미해결 계약 지적사항은 준비 완료를 차단합니다. 다른 사람이 실행하도록 만든 명령문은 실행 증거가 아닙니다.

## 10. 최종 Human Review와 허가

최종 대상 리비전과 요청하는 통합 행위를 제시하고 사람의 명시적 승인을 받습니다. 설계 승인이나 Reviewer PASS는 병합·작업 종료·릴리스를 허가하지 않습니다. 문서화되어 실제로 적용 가능한 저위험 위임 정책만 대안이 될 수 있으며, 정책 출처와 적용 조건 충족 여부를 기록합니다.

승인은 필수 증거를 대신하지 못합니다. 후보가 의미 있게 바뀌면 영향받는 검증·검토·승인을 다시 확인합니다. 허가 전에는 **Human Review 준비 완료**라고 보고하고, 병합 또는 전체 완료라고 표현하지 않습니다.

## 11. 허가된 통합과 정리

실제 허가 범위 안에서만 병합, 작업 항목 갱신·종료, 임시 SDD 산출물과 격리 작업 공간 정리, 작업 레인 해제를 수행합니다. 로컬 보존 정책상 필요한 증거를 남기고 관련 없는 변경은 삭제하지 않습니다. 릴리스·배포가 허가 범위에 없다면 별도 권한이 필요합니다.

실제로 수행한 내용을 보고합니다. 승인된 구현 작업은 후보 형태로 전달할 수 있지만, 통합 생명주기 전체가 끝났다고 주장하지 않습니다.

선택적 [완료 증거 보존 예시](../examples/completion-evidence/README.md)는 승인 설계 checkpoint, 최종 후보의 AC·검토·위험 요약, 허가된 통합, 이슈 전용 산물 정리를 연결합니다. 임시 원본을 제거하기 전에 보존 증거를 계속 조회할 수 있는지 확인하는 사례입니다. 공통 저장 시스템을 지정하거나 작은 작업에 Large 산출물을 추가하지 않습니다.
