# 워크플로

## 1. 이슈 정의

우선순위, SDD 등급, 사용자 영향, 목표, 범위·비범위, 허용·금지 경로, 인수 조건, 의존성·차단 요소를 정의합니다.

구현 에이전트가 시작하기 전에 이슈에서 문제의 범위를 좁힙니다.

## 2. 사전 점검

코드를 수정하기 전에 다음을 확인합니다.

- 필수 이슈 필드가 있는지 확인합니다.
- 레이블·메타데이터가 본문과 일치하는지 확인합니다.
- 차단 요소가 해결되었는지 확인합니다.
- 요청된 작업을 시작해도 되는지 확인합니다.
- 범위 경계를 실제로 적용할 수 있는지 확인합니다.

필수 경계나 의존성을 안전하게 판단할 수 없다면 작업을 허용하지 않는 방향으로 처리합니다.

## 3. 작업 선점 / 격리

병렬 에이전트 작업에서는 다음을 수행합니다.

- 이슈·레인을 선점합니다.
- 진행 중인 작업과 겹치는지 확인합니다.
- 격리된 브랜치·worktree·sandbox를 만듭니다.
- 제품 변경을 허용된 경계 안으로 제한합니다.

공유 경로나 통합 담당 경로는 일반 작업 레인에서 암묵적으로 수정하지 말고 별도로 분리해야 합니다.

## 4. AS-IS 분석

현재 메인라인 코드에서 시작합니다.

다음 순서를 권장합니다.

1. 직접 대상 경로
2. 대상 심볼
3. 직접 공개 계약
4. 직접 호출자·피호출자
5. 증거가 요구하는 경우에만 더 넓은 탐색

관찰된 동작, 관련 코드 위치, 의미 있는 불일치를 기록합니다.

## 5. TO-BE 설계

원하는 동작, 변경되지 않아야 할 동작, 실패·오류 동작, 필요한 경우 상태 전이, 검증 전략, 변경 계획을 정의합니다.

## 6. 트레이드오프 기록

실제 경쟁 선택지가 이미 드러난 경우에만 기록합니다. 템플릿을 채우기 위해 대안을 만들지 않습니다.

## 7. 위험 등급 게이트

위험 등급에 필요한 최소한의 절차를 적용합니다.

## 8. 구현

- 허용된 파일만 변경합니다.
- 관련 없는 리팩터링·기능을 추가하지 않습니다.
- 직접적인 회귀 테스트를 추가합니다.
- 구현이 인수 조건과 일치하도록 유지합니다.

## 9. 검증

대상 중심 검증을 먼저 실행합니다. 변경 범위상 필요하다면 더 광범위한 검증을 수행해야 합니다.

## 10. 자체 검토

최종 diff를 이슈 범위, 인수 조건, 허용·금지 경계, 의도하지 않은 동작 변경과 비교합니다.

## 11. 지속 관리되는 제품 문서 + 최종 검증

런타임·제품 동작이 변경되었다면 SDD 문구를 복사하지 말고 **최종 코드 동작**을 기준으로 지속 관리되는 제품 문서를 갱신합니다. 그런 다음 필수 최종 검증을 실행합니다.

## 12. PR / 코드 검토

PR은 이슈 범위와 일치해야 하며, 검증 증거와 미검증 항목을 명시하고, 등급에 맞는 검토 게이트를 적용해야 합니다.

## 13. 조건부 실기기 QA

변경에 실기기 증거가 필요하다면, 필수 관찰 결과를 수집하고 인수 조건에 따라 판정할 때까지 PR 병합을 차단합니다.

## 14. 병합 / 정리 / 해제

필수 증거가 통과하면 병합하고, 이슈를 닫고, 임시 SDD 산출물을 제거하고, 격리된 작업 공간을 정리하고, 작업 레인을 해제합니다.
