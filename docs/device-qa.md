# 조건부 실기기 QA

실기기 QA는 **조건부 병합 게이트**이며, 모든 Pull Request에 적용되는 필수 절차가 아닙니다.

## 일반적인 적용 조건

다음 항목에 따라 인수 조건의 충족 여부가 달라진다면 실기기 QA를 고려합니다.

- 실제 UI·UX 상호작용
- 카메라·파일·미디어의 업로드, 표시 또는 다운로드
- 권한
- 알림
- 생명주기 동작
- 백그라운드 스케줄링·실행
- 마이그레이션 이후의 실제 애플리케이션 흐름
- 단위 테스트나 에뮬레이터로 신뢰성 있게 입증할 수 없는 기기·플랫폼 동작

## 흐름

```text
검증 전략
  -> 실기기 QA가 필요한가?
      -> 아니요: 일반 검토·CI 경로
      -> 예:
          PR에 실기기 QA REQUIRED 표시
          -> 인수 조건 기반 체크리스트
          -> 관찰 결과 수집
          -> PASS / FAIL / UNVERIFIED 판정
          -> 필수 항목이 PASS여야 병합 가능
```

## 관찰과 판정을 분리

다음과 같이 역할을 분리하면 안전성을 높일 수 있습니다.

- **수집자(collector)**는 관찰 결과와 증거를 기록합니다.
- **판정자(judge)**는 이를 인수 조건과 비교합니다.

수집자는 제품 요구사항을 추가로 만들어 내거나 광범위한 제품 탐색을 수행해서는 안 됩니다.

## 체크리스트의 출처

QA 체크리스트는 다음을 바탕으로 작성합니다.

1. 이슈의 인수 조건
2. 실제로 변경된 사용자·런타임 흐름

이슈가 탐색적 QA를 명시적으로 요구하지 않는 한, 구현 후에 QA 에이전트에게 새로운 테스트 전략을 브레인스토밍하도록 요청하지 않습니다.

## 보고서 예시

```md
## 실기기 QA

- 빌드·커밋: abc123
- 기기·환경: ...
- 시간: ...

| 인수 조건 | 예상 결과 | 관찰 결과 | 증거 |
| --- | --- | --- | --- |
| 변경된 화면을 열 수 있음 | 화면에 진입할 수 있음 | 정상적으로 진입함 | 스크린샷 / 로그 ID |

### 판정
- PASS / FAIL / UNVERIFIED
```

필수 증거가 FAIL 또는 UNVERIFIED라면 병합은 계속 차단됩니다.
